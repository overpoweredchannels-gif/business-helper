# Desktop Route Classification — Aankh (HYBRID fix basis)

Classified at origin/main tip `d813dc937c54def26fe427ec9082f554beb30aeb` (`d813dc9` — "Slice 0: desktop route classification CI gate"), 2026-11-19.
Read-only classification: every route file under `src/app/api/**/route.ts` was enumerated with `find` (125 files) and its data access traced in code — direct `createSupabaseService()` calls, one-level service/repository traces, direct `SUPABASE_SERVICE_ROLE_KEY` use, and server-side API keys (Gemini, Google Maps). No route was executed; "Desktop today" is derived from the access pattern, not a runtime probe.

Classes: **CLOUD** = must run on Vercel (needs the service key, admin power, or a server-side API key the desktop never ships). **LOCAL** = works on desktop as-is (caller JWT or no DB), or is fixed desktop-side with no server call (Walk-in seed record). **USER-JWT** = deferred — the fix is a user-JWT rewrite, but ONLY after the RLS audit, route by route; it is not the fix now.

## 1. Summary

- Total routes: **125** — CLOUD **41**, LOCAL **16**, USER-JWT (deferred) **68**.
- Called from desktop (static grep over `src/app/page.tsx`, `src/components`, `src/lib`, `src/app`): **106** routes; **19** routes have no static desktop caller (listed in the table; see section 7 for the dynamic-URL caveat).
- Direct `createSupabaseService()` in the route file: 69 routes. Service-backed via a one-level lib import: 39 routes (of which 13 are false positives — the module only exports/uses `createSupabaseUserClient`; corrected in the table). Direct `SUPABASE_SERVICE_ROLE_KEY` use bypassing the helper: 3 routes (`/api/location/current`, `/api/location/device-session`, `/api/location/upload`) — a plain `createSupabaseService` grep misses these.
- The desktop build ships only `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` (`.github/workflows/desktop.yml:45-48`); no Gemini key, no Google Maps key, no service key. Any route needing one of those is CLOUD by construction.

## 4. Purchase-queue preservation — verified (the fix must not drop already-queued offline purchases)

Queue table `local_purchases` (`electron/store.ts:624-635`): `id TEXT PRIMARY KEY, scope, input_json, provisional_number UNIQUE, synced INTEGER DEFAULT 0, server_id, sync_status DEFAULT 'pending', sync_error, created_at, updated_at`. The row `id` IS the idempotency / request key: `submitPurchase` sends `request_key: row.id` (`src/lib/offline/purchase-sync.ts:120`). Scope is `orgId:profileId`.

`syncOnePurchase` (`src/lib/offline/purchase-sync.ts:253-330`):
- Status-check first via the `get_purchase_request_status` RPC (`:299-308`): a lost POST response is recovered, not duplicated. Until the S6 SQL (`get_purchase_request_status.sql`) is run on production the check throws and the submit below runs — same as a lost response; idempotent via the unique `purchase_transactions.request_key`.
- 5xx / network / 401 / 403 → returns `"queued"` (`:315-316`): the row is untouched and retried on the next trigger.
- Any unexpected failure → `"queued"` (`:326-327`).
- Only a definitive 4xx parks the row: `markRejected` upserts the row with `syncStatus: "rejected"` (`:264-271` — the row is KEPT) and parks a visible Sync Issue (`:320-324`). Header doc (`:33`): "The parked row is never auto-deleted."
- The ONLY removal path is `confirmRow` (`:272-295`), which deletes the local row (`backend.remove(scope, row.id)`, `:286`) AFTER the server confirms the purchase — and even a failed remove is harmless ("A leftover row replays harmlessly (same key → replay)").

**Conclusion: no path in the sync engine deletes or drops an unconfirmed purchase. The fix can re-drive every queued row with its existing idempotency key.**

The ONE drop risk is outside the engine, in the online save path (`src/app/page.tsx:11205-11230`): `createPurchase` throwing parks locally via `savePurchaseLocally()` ONLY when `isNetworkError(caught)` is true; a server 500 (or any non-network throw) is re-thrown and the purchase is lost — it never enters `local_purchases`. The hybrid fix must park on 500 too (`savePurchaseLocally`, `page.tsx:11177-11195`, writes `newLocalPurchaseRow` + `upsert` to `local_purchases`).

## 8. CI-gate design (for the fix phase — script NOT written here)

Manifest: `DESKTOP_ROUTE_CLASSIFICATION.json` (generated alongside this file from the same data; route → classification + methods + called-from-desktop). The `.md` table is rendered from it — the JSON is the single source of truth; the script must never hand-edit the table without regenerating the JSON.

New script (to be written in the fix phase): `scripts/check-desktop-routes.mjs`, run in `.github/workflows/desktop.yml` BEFORE the packaging step (after `npm ci`, before `electron-builder`). It must exit non-zero (fail the build) on any of:

1. **Unclassified route.** Enumerate `find src/app/api -name route.ts`, normalise each path to `/api/...` (strip `src/app/api`, strip `/route.ts`, `[id]` stays literal), and require an entry in the manifest. Also fail on manifest entries with no matching file (stale entry). This is the load-bearing rule: a new route cannot ship to desktop unclassified.
2. **LOCAL / USER-JWT route using the service key.** For every manifest entry classified LOCAL, grep its route file (and its one-level lib imports: the files it imports from `@/lib/**`) for `createSupabaseService` and for `SUPABASE_SERVICE_ROLE_KEY`. Any hit fails. (USER-JWT entries are allowed to still contain it until their conversion lands — but the script must report them as "pending conversion" in the log; once an entry is converted, its class stays USER-JWT and the same grep applies. Simpler: the script treats LOCAL and USER-JWT identically for this rule AFTER the conversion PR for that route lands — the conversion PR flips a `converted: true` flag in the manifest, and the grep applies to converted entries.)
3. **Service key in desktop packaging files.** `grep -rn "SUPABASE_SERVICE_ROLE_KEY" electron/ .github/workflows/desktop.yml` must return nothing. And no assignment anywhere it could be consumed: `grep -rn "SUPABASE_SERVICE_ROLE_KEY=" --include="*.yml" --include="*.yaml" --include="*.env*" --include="*.json" .` (excluding `node_modules`) must return nothing. NOTE: `src/lib/supabase/server.ts` legitimately reads `process.env.SUPABASE_SERVICE_ROLE_KEY` — that file is NOT in the checked set; the check is scoped to desktop packaging, not the web server code.
4. **Desktop env allowlist.** In `.github/workflows/desktop.yml`, the `env:` block of the build job must contain ONLY `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (allowlist). Any other `NEXT_PUBLIC_*` or secret var fails. (Audit M10: also fail fast when either variable is empty, and add `permissions: contents: write` to the workflow.)
5. **CLOUD routes not called directly from desktop code.** The renderer must reach CLOUD routes only through the cloud-endpoint helper introduced in the fix phase (name TBD, e.g. `cloudFetch` in `src/lib/offline/cloud-endpoints.ts`). The script greps `src/app/page.tsx`, `src/components`, `src/lib` for direct `fetch(`/`authorizedFetch(` calls whose literal path is a CLOUD route, excluding the helper module itself. Any direct call fails. (Static grep; dynamic URLs are a known gap — see section 7.)
6. **Version / tag guard (audit M9).** On a tag build, fail if the tag (`vX.Y.Z`) does not equal `package.json` version (`X.Y.Z`). A `v0.1.0` release from any other commit would otherwise never auto-update run-#5 users (same version number).
7. **Desktop smoke test (runtime, after packaging, before artifact upload).** Boot the packaged standalone server with the desktop env and: (a) `GET /login` returns 200; (b) a CLOUD route (e.g. `GET /api/products/list` without auth) returns the missing-service-key 500 — proving no key leaked into the bundle/env; (c) a LOCAL route that needs no auth returns its normal unauthenticated response (401/403, not 500). Grep the smoke run's `server.log` for a leaked key value pattern is NOT possible (the value lives only in Vercel/GitHub secrets) — the guarantee is rules 3–4, not log scanning.

What the gate CANNOT check (state plainly in the workflow log): the literal service-role key value (it never exists in the repo); RLS policies (they live in production Supabase — the USER-JWT conversion PRs must each cite the verified policy); RPC grants; storage bucket policies.

### Slice 0 implementation notes (gate built 2026-11-19, branch `hybrid-slice-0-ci-gate`)

Script: `scripts/check-desktop-routes.mjs` (Node stdlib only), wired into `.github/workflows/desktop.yml` after `npm ci` (static checks) and after packaging (smoke step, before artifact upload). Manifest entries may carry two optional fields: `migrated: true` (enforcement switch — Bearer/org-from-token hardening + no direct renderer fetch outside the cloud helper) and `pending: "<slice>"` (known exception, reported not failed; only `/api/sales/walk-in` today, pending Slice 5).

Deviations from the §8 design above, found while implementing (safer variant kept):
- Rule 2 as literally written (grep route file + one-level lib imports for the helper *name*) flags 13 of 16 LOCAL routes — they import `src/lib/supabase/server.ts` (the module that *defines* the helper; importing it is not calling it) or `src/lib/identity/api-context.ts` (resolveActor: service call inside try/catch, degrades to role permissions). The gate tests for actual *call* sites, excludes the factory module, and allowlists the two verified-guarded modules (`api-context.ts`; `invoice-number-service.ts` — service client only in the constructor `??` fallback, and the gate verifies the route imports only `*WithClient`/pure symbols from it). A new lib module that calls the helper fails the gate.
- Rule 5 as literally written ("any direct fetch of a CLOUD route fails until the helper lands") fails on the real manifest: 48 direct CLOUD fetches exist in renderer code today, because the desktop currently points them at the local server — the bug Slices 1–6 fix. The gate enforces rule 5 per-route via `migrated: true` and reports unmigrated fetches as pending migration.
- Rule 7's example CLOUD probe (GET `/api/products/list`, unauthenticated) does not 500: that route is USER-JWT and checks auth first (403 before any service call). The smoke probe instead POSTs `/api/auth/provision` with a fake Bearer token, which reaches service-client creation before any user lookup and must 500 with "Service client creation failed".

Ratchet on pending direct CLOUD fetches (UMAIR item 4, 2026-11-19): the count of direct renderer fetches of unmigrated CLOUD routes was 39, then 47 — it must never grow again. The manifest stores the baseline as top-level `ratchet.pending_direct_cloud_fetches` (47); the gate fails when the computed count exceeds it and passes at or below it. The same commit that migrates routes (sets `migrated: true`) must lower the baseline to the new count; never raise it. The count uses check 5's exact/segment matching, not substring.

Pre-push enforcement (UMAIR item 2, 2026-11-19): direct pushes to main are blocked locally before they leave the machine. `npm install` / `npm ci` runs the `prepare` script in package.json, which installs `.git/hooks/pre-push` (`scripts/install-pre-push-hook.mjs`, Node stdlib only, zero new dependencies — no husky, no committed hook directory, no per-machine setup). The hook runs the gate (`node scripts/check-desktop-routes.mjs`) and a failing gate blocks the push — e.g. a new route with no manifest entry. The gate takes ~1s, so the hook stays fast. CI ("Desktop route classification gate" workflow) is only the last safety net, for machines that pulled without running `npm install`. If a different pre-push hook already exists, the installer leaves it untouched and warns instead of overwriting it.
